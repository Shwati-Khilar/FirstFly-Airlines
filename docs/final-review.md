## Verified data and architecture

- Of these, seed registry owns **120 DEMO flights, 10,800 seats**. Existing 20 flights/1,800 seats are not presented as generated by the new seed.
- **11 tables**: users, flights, seats, passengers, bookings, auth_sessions, reservation_attempts, payment_records, payment_webhook_events, auth_rate_limits, demo_flights.
- **17 implemented API method/path pairs**, enumerated in README. /api/seats/confirm is a compatibility alias, not a second finalizer. Route inventory is not a claim of 17 live-provider end-to-end tests.
- Clean-database verification passed: migrations twice, seed twice with no duplicates, bcrypt registration, session validation, seat lock/release; temporary database removed.
- Benchmark: **20 requests, 1 successful reservation, 19 conflicts, 0 unexpected errors; 140.49 ms request batch, 645.95 ms full run**. Database: one matching active lock/reservation; zero passenger bookings or payments; cleanup verified. It measures local shared-handler HTTP plus MariaDB, not full Next.js throughput or production load.

The shared finalization handler verifies an owned persisted attempt and provider payment, then transactionally inserts one passenger booking and marks the seat booked. Row locks serialize seat acquisition; unique attempt/payment constraints arbitrate retries. Cancellation checks owner, preserves history, and releases inventory transactionally. Check-in is a protected booking lookup. Payment tests use mocks and real SDK signature helpers; no real Razorpay payment or delivered webhook was tested.

## Existing data concerns

Read-only audit: 5 active duplicate seat groups, 26 passenger rows without a valid owner, 19 rows without an exact canonical seat match, 17 active booking/inventory mismatches, 7 expired locks, no duplicate PNRs or payment IDs. These are legacy counts, not new generated bookings. Exact-seat mismatch includes old label conventions. Expired locks are handled logically and are not themselves proof of corruption. Records were not repaired or deleted; conflicting inventory remains blocked. Use the newly seeded inventory for demonstrations.

## Remaining limitations

This is a portfolio demonstration, not an airline production system. Browser checkout, PDF rendering, device responsiveness and real provider delivery still need manual testing. Refunds, ambiguous/late captures, chargebacks and legacy repair require review. There is no automatic reconciliation schedule, email verification, password reset, social login, MFA, signed boarding pass or persisted operational check-in state. Status telemetry is simulated. My Trips is unpaginated, deep flight offsets remain linear, and rate limits need deployment tuning. Build-time Google fonts require network access. A fresh npm ci installation from the updated lockfile passed in a temporary directory using the local cache; isolated empty-database bootstrap also passed. A different-machine deployment remains untested.

## Interview talking points

1. Why row-level locking plus conditional updates and uniqueness constraints are complementary.
2. Why reservation attempt IDs differ from payment IDs, and how retries converge on one booking.
3. Why a database transaction must not stay open across external checkout.
4. How a captured payment can require review after lease expiry without stealing a seat.
5. Why HTTP-only opaque sessions and server-side ownership checks replace client user IDs.
6. Why indexes were chosen from predicates/EXPLAIN, and why small timings did not justify a speedup claim.
7. Why additive migrations and isolated test databases preserve legacy customer data.
